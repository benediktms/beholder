# Beholder OpenSpec

OpenSpec is Beholder's sole workflow for behavioral contracts and architecture
decisions. The location of a statement identifies its role:

| Information | Authoritative location |
| --- | --- |
| Current observable behavior | `specs/` |
| Proposed behavior | `changes/<change>/specs/` |
| Change motivation and scope | `changes/<change>/proposal.md` |
| Architecture rationale and rejected alternatives | `changes/<change>/design.md` |
| Implementation plan and progress | `changes/<change>/tasks.md` |
| Completed decision history | `changes/archive/` |

Supporting documents remain under `../docs/` when their primary purpose is product
direction, measurement, operation, or explanation. They are not behavioral contracts.
When supporting material disagrees with a current spec, the spec governs current
behavior. Future sections of `../docs/VISION.md` remain direction until a reviewed
OpenSpec change introduces them.

## Change workflow

Use the repository-local Codex skills generated by OpenSpec:

1. `$openspec-explore` to investigate without changing implementation.
2. `$openspec-propose` to create a proposal, delta specs, design, and tasks.
3. `$openspec-apply-change` after the planning artifacts are approved.
4. `$openspec-update-change` when implementation changes the plan.
5. `$openspec-sync-specs` to merge completed behavioral deltas into current specs.
6. `$openspec-archive-change` after implementation, synchronization, and verification.

A documentation, refactoring, or tooling change with no observable behavior change
must set `skip_specs: true` instead of inventing a requirement. A behavioral change
must remain a delta under `changes/` until implementation is complete and the delta
has been synchronized into `specs/`.

Architecture choices are recorded in the active change's `design.md`. Once the
change is archived, that design is the durable decision record. Use descriptive
change names and inspect `changes/archive/` when earlier rationale constrains new
work.

## Validation and maintenance

Run the version pinned in `../mise.toml`:

```bash
mise exec -- openspec status --change <change-name>
mise exec -- openspec validate --all --strict
```

Run `mise exec -- openspec update` after upgrading the pinned OpenSpec version so
the repository-local skills remain compatible with the CLI.
